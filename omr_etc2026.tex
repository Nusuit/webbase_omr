\begin{abstract}
Browser-based Optical Mark Recognition (OMR) can keep student answer
sheets on the device and needs no application install, but how its cost
distributes across processing stages and platforms has not been measured.
This paper contributes a cross-platform benchmark of a complete Web Edge
OMR pipeline that pairs WebAssembly (\wasm{}) computer vision with WebGPU
YOLO inference, measured against a Native Android baseline on a
human-reviewed corpus of 185 answer sheets and seven Web hosts. We report
recognition accuracy, per-stage latency, and resource use for two
interchangeable configurations: a CV-only pipeline at 99.03\% question
accuracy, and a YOLO corner-keypoint detector that feeds four predicted
markers into the homography, matching that accuracy at 99.45\% across three
devices and reaching the same 99.44\% when ported to Native, while moving
the localization stage onto the GPU and skipping the hand-written marker
detection. The latency data localize the cost: on the same Redmi
device the \wasm{} CV core is $5.7\times$ slower than Native ($503$ vs
$89$\,ms), against only $1.6\times$ between WebGPU and NNAPI inference.
These measurements indicate that WebGPU has already made YOLO inference a
secondary cost, while the deterministic CV stage executed through \wasm{}
governs end-to-end latency, so a competitive Web Edge OMR depends on
reducing \wasm{} CV overhead rather than on accelerating the detector.
\end{abstract}

\section{Introduction}

Automated grading of multiple-choice answer sheets is widely used in
educational institutions, where large volumes of sheets must be
processed accurately within a short time. Existing deployments follow
two established patterns. Server-based services transmit scanned or
photographed sheets to remote infrastructure, introducing network
dependency and exposing student data to external
systems~\cite{patel2015,okorie2022}. Native mobile applications avoid
data transmission but require platform-specific packaging, app-store
distribution, and per-platform maintenance overhead.

Recent maturation of \wasm{} and WebGPU now allows computer-vision and
deep-learning workloads to execute directly inside modern browsers
without plugins or installation, which enables a third deployment model:
a fully client-side pipeline in which answer-sheet images are processed
within the browser and never leave the device. Because a single
URL-deployed bundle serves both desktop and mobile browsers, this model
avoids the data-exposure risk inherent in server-side grading while also
removing the installation friction of a native application.

In the browser these workloads map onto two different substrates. The
classical image-processing stages, namely perspective rectification,
adaptive thresholding, and fixed-grid bubble reading, are compiled from
C\texttt{++}/OpenCV to \wasm{} and run on the CPU, whereas sheet-region
localization can optionally be offloaded to neural inference through ONNX
Runtime Web on a WebGPU backend. A deployment may thus run a CV-only
pipeline or add a YOLO detector for the localization step; because the two
substrates use different browser APIs and hardware, it is their relative
cost rather than either component in isolation that determines whether a
given configuration can rival native execution. This benchmark measures
both.

This paper accordingly asks whether WebGPU inference, on its own, is
sufficient to make a Web Edge OMR pipeline competitive with Native
Android. Under the measured workload the answer is negative: WebGPU does
reduce YOLO latency, but the deterministic CV/\wasm{} stage then comes to
dominate end-to-end behavior. This leaves Native Android as the
lower-latency deployment, while Web Edge stands as the privacy-preserving
and URL-deployed alternative whose competitiveness depends on bounding
that \wasm{} CV stage.

The paper makes three contributions:
\begin{enumerate}[leftmargin=*, itemsep=1pt, topsep=2pt]
  \item A reviewed cross-platform OMR benchmark on a 185-sheet set with
  supervised accuracy, latency, and resource measurements across seven Web
  Edge hosts and one Native Android baseline.
  \item A stage-attribution result showing that \wasm{} OMR, not YOLO
  inference, is the dominant bottleneck: on the same Redmi device the CV
  \texttt{cpp\_ms} gap between Mobile Web and Native is $5.7\times$
  ($503$ vs $89$\,ms), whereas the WebGPU-versus-NNAPI gap for the same
  corner detector is only $1.6\times$ ($547$ vs $335$\,ms).
  \item A corner-keypoint formulation that turns YOLO into a validated
  primary detector: feeding the four predicted corner markers directly to
  the homography reaches 99.45\% across three devices, on par with the
  99.03\% CV baseline, while relocating the localization stage from the CPU
  to the GPU and dispensing with the hand-written marker detection and its
  second re-detection pass.
\end{enumerate}

\section{Related Work}

\paragraph{Classical OMR}
Traditional OMR pipelines rely on handcrafted image-processing
techniques such as thresholding, edge detection, and morphological
operations for bubble localization and recognition~\cite{patel2015,okorie2022}.
Although computationally efficient, these methods remain sensitive to
illumination variation and geometric distortion in mobile capture
scenarios~\cite{afifi2019}.

\paragraph{Deep learning for OMR}
Recent studies adopt YOLO-based detectors~\cite{redmon2016} to improve
robustness under challenging imaging conditions. Ali et
al.~\cite{ali2025} show that YOLO achieves higher detection accuracy and
better generalization than threshold-based approaches, while
YOLOv8n~\cite{jocher2023} provides a lightweight architecture suitable
for edge deployment. Tabassum and Rahman~\cite{tabassum2024} deploy
YOLOv8 for mobile OMR but report neither stage-level latency
decomposition nor a controlled cross-platform comparison, leaving
unclear how inference cost relates to the surrounding CV pipeline on
constrained devices.

\paragraph{Browser-based edge computing}
\wasm{} and WebGPU together enable privacy-preserving client-side
execution in modern browsers, with neural inference exposed through ONNX
Runtime Web~\cite{microsoft2021}. Quantitative evidence on the associated
overhead is already available: Jangda et al.~\cite{jangda2019} report
that \wasm{} runs on average 45\% slower than native code on
compute-intensive benchmarks, a margin that is directly relevant to
C\texttt{++} image-processing workloads compiled to \wasm{}, and Wang et
al.~\cite{wang2024} measure browser deep-learning inference at
$16.9\times$ slower than native on CPU and $4.9\times$ on GPU, with
WebGPU emerging as the strongest browser-side back-end. These studies,
however, characterize isolated kernels rather than complete
computer-vision pipelines. A higher-level abstraction is also emerging in
the W3C WebNN API~\cite{webnn2024}, yet it remains a draft, so the
practical interaction between \wasm{}-based image processing and WebGPU
inference within a full application is still poorly understood.

\paragraph{Research gap}
Prior work thus examines either OMR accuracy or browser inference
performance, but rarely both within one system. We are not aware of a
study that evaluates a fully client-side browser OMR pipeline in which
computer vision and neural inference both execute locally, without any
transmission of answer-sheet data to external servers. It likewise
remains open whether end-to-end latency on such a pipeline is governed by
neural inference or by the \wasm{}-executed computer-vision stages. The
present paper closes these gaps through controlled per-stage profiling of
a YOLOv8n-based browser OMR system across several execution back-ends and
deployment configurations.

\subsection{Cross-Platform System Architecture}
The system is organized as the layered runtime shown in
Fig.~\ref{fig:arch}(a), where each layer hides the one beneath it so that
the same application code runs unchanged on heterogeneous hardware. At the
top, the JavaScript main thread owns user interaction and image
acquisition from a camera stream or an uploaded file, but it delegates all
computation to a dedicated Web Worker so that heavy processing never
blocks UI responsiveness. Within the worker, an Algorithm Dispatcher
selects between a conventional CV-only pipeline and a hybrid YOLO$+$CV
pipeline; in the hybrid case it drives an ONNX YOLO model on a WebGPU
backend for localization, while the \wasm{} OMR core built on OpenCV.js
performs the actual recognition and grading. Since the dispatcher feeds
any localization output into that same \wasm{} core, the two pipelines
remain interchangeable at the recognition stage. Both back-ends ultimately
execute inside the OS and browser sandbox, which mediates scheduling,
memory, and security before mapping the work onto whatever CPU, GPU, or
NPU the device exposes. This separation between application control,
algorithm execution, and hardware access is what lets a single codebase
target desktop and mobile platforms without modification.

\subsection{Pipeline}

Fig.~\ref{fig:arch}(b) traces a single sheet from capture to score along
a predominantly linear spine, comprising the Input Frame, JS Decode \&
Prep, Method Selection, a detect stage, Fixed Grid Bubble Detection, and
Grade Output. Detection is the only stage that forks: it splits into a CV
branch and a YOLO branch, both of which converge again before grading so
that the remainder of the pipeline is identical in either configuration.

The main thread first hands the worker a raw frame or uploaded image,
here at $1{,}145\times2{,}560$\,px. \emph{JS Decode \& Prep} renders this
image onto a canvas and derives the two artifacts that the downstream
stages require, namely an RGBA pixel buffer for the \wasm{} core and,
whenever the hybrid path is selected, a letterboxed tensor for the YOLO
detector ($960\times960$ for the primary corner-keypoint model).
\emph{Method Selection} then routes the image into one of the
two detect branches. Because each branch performs the single task of
placing the answer grid at known coordinates and both subsequently feed
the same recognizer, the chosen branch alters only how the sheet is
located, never how an answer is ultimately read.

On the CV branch, the \wasm{} core recovers the page geometry without
external guidance. The \emph{Normalize} stage thresholds the image,
extracts connected components, and retains the four corner registration
markers by filtering candidate blobs on area, aspect ratio, and fill;
when that marker route proves unreliable, it instead falls back to the
white paper boundary. From the four resulting reference points it
estimates a homography onto a canonical $1700\times2400$ template, which
the \emph{Marker Crop} stage applies so that the answer grid is brought
to fixed positions.

On the YOLO branch, the primary configuration is a corner-keypoint
detector. The image is \emph{letterboxed} into a $960\times960$ square,
that is, scaled to fit while preserving its aspect ratio and padding the
leftover margin, and a single-class YOLOv8n model (\texttt{marker\_corners})
then runs on this square input through the WebGPU backend. The four
highest-confidence detections are reduced to their centres, geometrically
ordered into top-left, top-right, bottom-right, and bottom-left, and passed
\emph{directly} to the homography that rectifies the sheet onto the
canonical template. This lets the \wasm{} core skip both the
connected-component blob detection of the CV \emph{Normalize} stage and the
second marker re-detection, so the YOLO branch rejoins the shared
recognizer only at the \emph{Adaptive Threshold} stage. YOLO thus
contributes localization alone, since the answer string is invariably
decoded by the CV recognizer rather than by the detector.

Feeding exact corner points rather than a region crop is what lets the
branch bypass the re-detection stage: the homography is fully determined by
the four centres, so no marker search on the warped image is required. This
is the property that
Section~\ref{sec:results-recognition} quantifies, where the corner-keypoint
path matches the CV baseline while removing that CPU-side stage.

Once the two branches have rejoined on a common rectified crop,
\emph{Adaptive Threshold} performs local blurring and thresholding, and
\emph{Fixed Grid Bubble Detection} reads the answers. As the sheet now
resides in template coordinates, the grid fixes every bubble center in
advance, so that each option can be scored by the foreground density
inside a circular sampling window and the scores can be normalized within
each row, which prevents a uniformly dark or faint scan from biasing the
decision. The final \emph{Grade Output} stage emits the decoded answer
string together with validity and suspicious-mark flags and the per-stage
timers reported throughout this paper.

This linear dependence carries a consequence that the accuracy results in
Section~\ref{sec:results-recognition} make concrete. Because the
recognizer is deterministic, any geometric error introduced before the
homography does not remain local but instead displaces the entire grid,
which is precisely why detector-guided cropping must be regarded as an
integral part of the recognition algorithm rather than a harmless
preprocessing step.

\subsection{Deployment Trade-offs}
The two targets are complementary in their trade-offs. Web Edge, built on
OpenCV.js and WebGPU, executes across platforms and deploys directly from
a URL without installation, although it pays for this portability through
browser sandboxing and only indirect access to hardware accelerators.
Native Android, built on the OpenCV Android SDK and ONNX Runtime Android,
instead reaches the hardware directly through providers such as NNAPI and
thereby achieves lower inference latency, at the cost of application
packaging and per-platform maintenance. What the two targets share is
nonetheless more consequential for this study than where they differ,
since both perform all computation on the device: neither transmits
answer-sheet data, neither requires a network connection at inference
time, and neither depends on server infrastructure. It is this common
on-device property that makes a like-for-like latency comparison between
them meaningful.

\section{Experimental Setup}

The $N{=}185$ evaluation set comprises every annotated sheet in the
corpus: 179 student answer sheets (the ``B\`ai l\`am'' images) and six
answer-key sheets, drawn from five sub-datasets and each captured at
$1{,}145\times2{,}560$\,px on a Redmi Note~13 Pro+. Answer sheets and
answer keys are the same printed form---a key merely carries the correct
marks---so both are recognized by the identical pipeline; the keys differ
only in that they additionally serve as the grading reference. These 185
sheets carry 9,810 valid question labels and 49,050 binary A/B/C/D/E
decisions behind every accuracy figure in this paper; a human-reviewed
CSV under \texttt{runs/accuracy\_eval/} marks invalid trailing questions
as \texttt{NA}. The corner-keypoint detector evaluated as the primary
localizer is trained on these 185 sheets, split 159 train / 26 validation
under the default Ultralytics YOLOv8n recipe and exported to ONNX for
in-browser WebGPU inference.

The Native Android target runs the same algorithmic stages through
platform-native runtimes: OpenCV via Kotlin/JNI for the CV core, and ONNX
Runtime Android for inference with CPU single-thread, CPU four-thread, and
NNAPI providers. It exports per-question labels aligned to the reviewed
ground truth, so it is evaluated for both accuracy and latency; the
corner-keypoint path in particular is ported to Native and reaches
recognition parity with the Web build (Section~\ref{sec:results-recognition}).
Web and Native share these stages at the source level but not in compiled form:
OpenCV version, memory layout, SIMD scheduling, floating-point ordering,
and image-buffer marshalling all differ between OpenCV.js and OpenCV
Android, so that identical inputs need not produce bit-identical outputs.
To keep the inference component itself comparable, both targets load the
same ONNX model and vary only the execution provider, which is WebGPU in
the browser and either CPU or NNAPI on Android.

Seven Web hosts replay the identical $N{=}185$ images: a desktop
reference (i5-14600K / RTX 4070 Ti SUPER), an ASUS Vivobook (i5-13500H),
an Acer Nitro~5 (i5-10300H), a MacBook Air M1, an iPhone~16
(Safari/WebKit), a Poco Pad M1 Android tablet (Chrome/Blink), and the
Redmi Note~13 Pro+ (Chrome/Blink), with the Native baseline running on
that same Redmi device. Web latency rows report worker-side
\texttt{cpp\_ms} whereas Native rows report file-based \texttt{e2e\_ms},
so that same-boundary tests are restricted to \texttt{cpp\_ms} on both
sides. Resource sampling relies on whichever instrument each host
exposes, namely \texttt{psutil} for Windows Chrome, an in-page
timer-lag proxy where direct process sampling is unavailable, and an
in-app sampler on Native.

\section{Results and Discussion}

\subsection{Recognition Accuracy}
\label{sec:results-recognition}

Table~\ref{tab:accuracy} reports supervised exact-match recognition on
the reviewed $N{=}185$ set. Traditional CV correctly recognizes 9,715 of
the 9,810 valid questions, a question-level accuracy of 99.03\%, and
reproduces every valid answer on 143 of the 185 sheets. Replacing the CV
sheet-localization stage with a YOLO corner-keypoint detector, which emits
the four corner registration markers and feeds their centres directly to
the homography, returns 99.45\% (9,756/9,810) and 155 of 185 fully correct
sheets. The two configurations are thus on par for accuracy: the corner
detector operates as a genuine primary localizer rather than a
preprocessor, and does so reproducibly, returning 99.44--99.45\% on every
repeated run across the mobile devices.

Because the two localizers reach the same accuracy, the value of the
corner-keypoint formulation lies elsewhere. Passing four exact corner
points to the homography removes the connected-component marker detection
and its second re-detection pass from the C\texttt{++} core and moves the
localization work onto the GPU; the latency results below show the
resulting shift in where the per-sheet cost is spent. At the bubble level
the CV baseline attains a Precision of 0.992, a Recall of 0.994, and an F1
of 0.993 over the 49,050 binary decisions, and the corner-keypoint
pipeline matches it there as well.

\subsection{Cross-Platform Latency}
\label{sec:latency}
Fig.~\ref{fig:latency} and Tables~\ref{tab:stage-mini}--\ref{tab:latency}
report the deployment benchmark, which confirms that WebGPU has already
reduced machine-learning inference to a secondary cost and that the
residual Web-versus-Native gap originates in the deterministic CV stage
rather than in the detector.

The clearest evidence is a same-device, same-boundary comparison on the
Redmi. For the CV core, measured as the \texttt{cpp\_ms} of the
C\texttt{++}/OpenCV OMR stage, Native Android requires only $89$\,ms
whereas the Mobile Web build requires $503$\,ms, a $5.7\times$ gap that
arises solely from executing the same algorithm through \wasm{}. The
learned stage behaves very differently: the corner detector takes
$547$\,ms on WebGPU against $335$\,ms for the Native NNAPI provider, a
$1.6\times$ gap that is far smaller than the $16.9\times$ CPU slowdown
reported for browser deep-learning inference in prior
work~\cite{wang2024}, which shows that WebGPU is already an effective
accelerator. Since the CV gap exceeds the inference gap and the CV stage
runs on every sheet irrespective of the detector, the first-order lever
for Web Edge latency is the \wasm{} CV runtime, not the detector back-end.

The Native budget reinforces this attribution and, with the corner path
ported across, removes the earlier Native accuracy gap
(Table~\ref{tab:stage-mini}). Excluding the debug-only JPEG write, the
Native CV core runs in $89$\,ms of \texttt{cpp} time, $5.7\times$ faster
than the same stage compiled to \wasm{} ($503$\,ms on this device); but the
hand-written CV marker search collapses on the dark-background
\texttt{dataset\_4/5} photos, where the faint printed corner markers are
missed, holding CV recognition to $87.2\%$. Porting the identical
corner-keypoint formulation to Native --- the same single-class corner
model, the same geometric corner ordering, and the same homography ---
closes that gap: the Native corner pipeline recognizes $99.44\%$ of
questions, on par with the Web hybrid ($99.45\%$) and correct on all five
sub-datasets including the dark sheets, at an inference cost of $335$\,ms
under NNAPI and $530$\,ms on four CPU threads. Compared like for like, the
corner detector runs only $1.6\times$ slower on WebGPU ($547$\,ms) than on
NNAPI ($335$\,ms), whereas the CV core is $5.7\times$ slower in \wasm{} than
native; the web-vs-native penalty is therefore concentrated in the \wasm{}
CV runtime, not in the GPU-accelerated detector. Native thus keeps the
lower end-to-end latency while now matching the Web pipeline's recognition
accuracy through the shared corner-keypoint path.

Within the browser, the corner-keypoint hybrid reshapes the cost
structure rather than merely adding to it. Table~\ref{tab:hybrid}
contrasts the CV-only and corner-keypoint pipelines on three devices, each
a five-run median, and two effects recur. First, the two pipelines reach
the same accuracy --- CV at 99.03\% and the hybrid at 99.45--99.46\% --- so
the choice of localizer is accuracy-neutral and the hybrid earns its place
on other grounds. Second, the corner path roughly halves the C\texttt{++}
\texttt{cpp\_ms}, because feeding an exact four-point geometry to the
homography lets the core skip both blob detection and the second marker
re-detection: the core falls from $503$ to $249$\,ms on the Redmi, from
$343$ to $166$\,ms on the Poco Pad, and from $325$ to $138$\,ms on the
Vivobook. Whether this yields a faster pipeline is device-dependent: on the
Vivobook the C\texttt{++} saving outweighs the added WebGPU inference and
worker time falls from $379$ to $278$\,ms, whereas on the phones the
$450$--$550$\,ms corner inference dominates and worker time rises (Redmi
$685\to803$\,ms). The hybrid thus moves the localization work off the
deterministic C\texttt{++} core and onto the GPU at identical accuracy,
trading inference latency for a lighter CV stage.

These traces also clarify why a lower browser CPU reading should not be
mistaken for higher throughput. The Web worker tends to stay within a
narrow, near single-core execution envelope precisely because the
deterministic CV core is compiled into \wasm{} and serialized through its
memory model, whereas Native OpenCV draws more sampled CPU but converts
those bursts into lower latency by means of native threading and direct
memory access. The implication is consistent with the latency analysis:
bounded resource use confirms deployability, yet competitiveness in
latency continues to depend on reducing the \wasm{} CV cost itself.

\subsection{Threats to Validity}
\label{sec:threats}
\begin{enumerate}[label=(\roman*), leftmargin=*, itemsep=1pt, topsep=2pt]
  \item CPU/RAM instruments differ across platforms, so resource values
  are reported with their native units and used for trend interpretation
  rather than direct cross-instrument ratios.
  \item The supervised accuracy artifact covers one 185-sheet
  fixed-template collection. This is the intended workload scope rather
  than a claim about arbitrary-layout OMR; writer-disjoint data and
  broader capture conditions remain future validation.
  \item Web and Native use matched source-level algorithmic stages, but
  OpenCV build, floating-point ordering, and memory layout still differ, so
  outputs are not bit-identical. The shared corner-keypoint path reaches
  Native parity ($99.44\%$ vs $99.45\%$); the Native CV-only path, by
  contrast, still loses the dark \texttt{dataset\_4/5} sheets ($87\%$)
  because its hand-written marker search is less robust than the Web build's.
  \item The corner-keypoint detector is trained on 185 sheets
  (validation $\mathrm{mAP}@0.5\approx 0.99$) drawn from one fixed-template
  collection; because these corner labels include the evaluation sheets,
  the 99.45\% figure reflects fiducial-localization fit on this template
  rather than writer-disjoint generalization.
  \item Web latency on thermally constrained laptops is sensitive to the
  host power plan and thermal state. On the Vivobook (i5-13500H) we
  observed up to a $\approx 2\times$ spread in per-sheet \texttt{cpp\_ms}
  across repeated High-Performance runs, driven by CPU/GPU clock
  throttling rather than algorithmic change (recognition outputs are
  bit-identical across runs). Every device in Table~\ref{tab:hybrid} is
  therefore reported as a five-run median, and the Web-versus-Native
  comparison is drawn on the same Redmi device to avoid this confound.
\end{enumerate}

\section{Conclusion}

Web Edge OMR proves to be both accurate and deployable, yet its latency
is determined by how the stages balance rather than by inference alone.
The reviewed Web CV path reaches 99.03\% question accuracy, and a YOLO
corner-keypoint detector that feeds four predicted markers straight into
the homography matches it at 99.45\% across three devices and, ported to
Native, reaches the same $99.44\%$ there as well, while moving localization
onto the GPU and removing the hand-written marker detection. On latency,
the dominant web-versus-native term is the \wasm{} CV stage: on the same
Redmi device its $503$\,ms is $5.7\times$ the $89$\,ms native core, a far
larger gap than the $1.6\times$ between WebGPU and NNAPI for the same
detector. Native Android therefore remains the faster deployment --- now at
matching accuracy --- while Web Edge exchanges that latency for privacy and
installation-free reach. Closing the remaining gap is
ultimately a question of browser-accessible CV acceleration and a leaner
\wasm{} runtime rather than of a faster detector.
