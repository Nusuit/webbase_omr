\begin{abstract}
Browser-based Optical Mark Recognition (OMR) enables on-device grading
without application installation, but the relative cost of the different
stages in a browser-side OMR pipeline has not been systematically quantified.
We present a Web Edge OMR framework and the first reported stage-wise cost
attribution of a fully client-side browser OMR pipeline that runs WebAssembly
(\wasm{}) computer vision and WebGPU YOLO inference locally on the device. We evaluate it on a 185-sheet fixed-template benchmark
across five browser/device configurations, with a Native Android baseline
for reference.
Our evaluation yields three findings. First, the web-versus-native latency gap is
dominated by the deterministic \wasm{} computer-vision core, which runs
$2.6\times$ slower than its Native counterpart (CV-only, matched boundaries).
Because this core runs on every sheet, it is the first-order target in the
CV-only path and the cost common to both configurations; the hybrid path
instead trades part of that CV cost for WebGPU inference. Second, despite this gap, both Web configurations exceed $99\%$ question
accuracy, and the corner-marker path matches this level when ported to Native
Android.
Third, adding a WebGPU corner-marker detector gives only a small accuracy
gain ($\sim\!0.4$ points), so detector outputs must be validated end-to-end
against the fixed-template recognizer rather than assumed from localization
quality. The corner-marker path reaches $99.46\%$ overall ($99.3\%$ on 101 unseen sheets).
These results support browser-based grading as an installation-free,
privacy-preserving option for on-device OMR.
\end{abstract}

\section{Introduction}

Automated grading of multiple-choice answer sheets is widely used in
educational institutions, where large volumes of sheets must be
processed accurately within a short time. Existing deployments follow
two established patterns. Server-based services transmit scanned or
photographed sheets to remote infrastructure, introducing network
dependency and exposing student data to external
systems~\cite{patel2015,okorie2022}. Native mobile applications avoid
data transmission but require platform-specific packaging, app-store
distribution, and per-platform maintenance overhead.

Recent maturation of \wasm{} and WebGPU now allows computer-vision and
deep-learning workloads to execute directly inside modern browsers
without plugins or installation, which enables a third deployment model:
a fully client-side pipeline in which answer-sheet images are processed
within the browser and never leave the device. Local execution therefore avoids the data-exposure risk inherent in server-side
grading, while a single URL-deployed bundle that serves both desktop and mobile
browsers removes the installation friction of a native application.

This heterogeneous model is promising, but its performance is not yet
understood. A browser OMR pipeline couples two very different substrates:
CPU-bound \wasm{} computer vision and GPU-accelerated neural inference, each
using distinct browser APIs and hardware. Existing work has not shown how these substrates interact inside a complete
recognition pipeline. It remains unclear where the dominant bottleneck lies,
whether WebGPU localization can offset the browser's latency disadvantage
relative to native execution, and whether a learned localizer improves
recognition enough to justify replacing the classical front-end. Because it is their relative cost,
not either component in isolation, that determines whether a configuration can
rival native deployment, both must be measured within the same pipeline.

To address this, we present a systematic empirical study that benchmarks a
complete Web Edge OMR pipeline, in both a CV-only and a hybrid YOLO+CV
configuration, against a Native Android baseline. Our analysis shows that although WebGPU makes YOLO inference an effective
accelerator, the deterministic \wasm{} computer-vision stage is the larger
source of the web-versus-native latency gap, and is therefore the primary
optimization target for browser-side OMR.

The paper makes three contributions:
\begin{enumerate}[leftmargin=*, itemsep=1pt, topsep=2pt]
  \item We construct and evaluate a human-reviewed 185-sheet fixed-template OMR
benchmark across five browser/device configurations, with supervised accuracy
and latency measurements, indicative resource measurements, and a Native
Android baseline on two devices.
  \item We perform a stage-level attribution analysis that separates
  browser-based computer vision and neural-inference costs, demonstrating
  that the web-versus-native latency gap is larger for the deterministic
  \wasm{} computer-vision stage than for WebGPU-accelerated YOLO inference.
  \item We evaluate a YOLO corner-marker handoff that offloads localization to WebGPU
while keeping recognition in the shared fixed-template CV core, and find a
small but measurable accuracy gain concentrated in low-contrast captures.
\end{enumerate}

\section{Related Work}

\paragraph{Classical OMR}
Traditional OMR pipelines rely on handcrafted image-processing
techniques such as thresholding, edge detection, and morphological operations that register each sheet to a fixed template and
read bubbles at predetermined grid positions~\cite{patel2015,okorie2022}.
Although computationally efficient, these methods remain sensitive to
illumination variation and geometric distortion in mobile capture
scenarios~\cite{afifi2019}.

\paragraph{Deep learning for OMR}
Recent studies adopt YOLO-based detectors~\cite{redmon2016} to improve
robustness under challenging imaging conditions. Ali et
al.~\cite{ali2025} summarize evidence that YOLO-based detectors improve
detection robustness over threshold-based methods, while
YOLOv8n~\cite{jocher2023} provides a lightweight architecture suitable
for edge deployment. Tabassum and Rahman~\cite{tabassum2024} deploy
YOLOv8 for mobile OMR but report neither stage-level latency
decomposition nor a controlled cross-platform comparison, leaving
unclear how inference cost relates to the surrounding CV pipeline on
constrained devices.

\paragraph{Browser-based edge computing}
\wasm{} and WebGPU~\cite{webgpu2025} together enable client-side execution in modern browsers, with neural inference exposed
through ONNX Runtime Web~\cite{microsoft2021}. Quantitative evidence on the associated
overhead is already available: Jangda et al.~\cite{jangda2019} report
that \wasm{} runs on average 45\% slower than native code on
compute-intensive benchmarks, a margin that is directly relevant to
C\texttt{++} image-processing workloads compiled to \wasm{}, and Wang et
al.~\cite{wang2024} measure browser deep-learning inference at
$16.9\times$ slower than native on CPU and $4.9\times$ on GPU, with
WebGPU emerging as the strongest browser-side back-end. These studies,
however, characterize isolated kernels rather than complete
computer-vision pipelines. A higher-level abstraction, the W3C WebNN API~\cite{webnn2026}, is also advancing through the W3C standardization process, but practical
client-side pipelines commonly still rely on \wasm{} and WebGPU, whose interaction within
a full application is poorly understood.

Prior work thus examines either OMR accuracy or browser inference performance,
but rarely both within one system: OMR studies omit browser-stage costs, while
browser-performance studies measure isolated kernels~\cite{jangda2019,wang2024}
rather than a complete recognition pipeline. The present paper bridges this by
profiling a full client-side OMR pipeline per stage, across several back-ends
and deployment configurations.

\section{System Architecture and Methods}

  \centering

JavaScript thread dispatches camera or file input to a Web Worker. (b) Per-sheet
pipeline: WebGPU accelerates only YOLO localization, while normalization,

  \label{fig:arch}

\subsection{Cross-Platform Layered Architecture}
The system is organized as the layered runtime shown in
Fig.~\ref{fig:arch}(a), where each layer hides the one beneath it so that
the same application code runs unchanged on heterogeneous hardware. At the
top, the JavaScript main thread owns user interaction and image
acquisition from a camera stream or an uploaded file, and rendering them onto a canvas, but it delegates all
computation to a dedicated Web Worker so that heavy processing never
blocks UI responsiveness. Within the worker, an Algorithm Dispatcher
is configured to run either a conventional CV-only pipeline or a hybrid
YOLO$+$CV pipeline to resolve the sheet corners; in the hybrid case it drives an ONNX YOLO model on a WebGPU
backend for localization, while the \wasm{} OMR core (hand-written
C\texttt{++} image-processing kernels together with OpenCV, compiled to
\wasm{} utilizing SIMD and multi-threading) performs the actual recognition and grading. Since the dispatcher feeds
any localization output into that same \wasm{} core, the two pipelines
remain interchangeable at the recognition stage. Both browser back-ends execute inside the browser sandbox, which mediates
scheduling, memory, and accelerator access before mapping work onto the
available CPU and GPU.

\subsection{Algorithmic Pipelines and Handoff Mechanism}

Fig.~\ref{fig:arch}(b) traces a single sheet from capture to score along
a predominantly linear spine, comprising the Input Frame, JS Decode \&
Prep, Method Selection, followed by parallel CV or YOLO detection branches, a shared Adaptive Threshold, Fixed Grid Bubble Detection, and
Grade Output. Detection is the only stage that forks: it splits into a CV
branch and a YOLO branch, both of which converge again before grading so
that the remainder of the pipeline is identical in either configuration.

The main thread first hands the worker a raw frame or uploaded image,
here at $1{,}145\times2{,}560$\,px. \emph{JS Decode \& Prep} renders this
image onto a canvas and derives the two artifacts that the downstream
stages require, namely an RGBA pixel buffer for the \wasm{} core and,
whenever the hybrid path is selected, a letterboxed tensor for the YOLO
detector ($960\times960$ for the primary corner-marker model).
The two branches correspond to deployment configurations selected explicitly
(the benchmark evaluates each separately) rather than chosen per sheet; within
the hybrid branch, the corner-warp path is taken when the detector returns four
boxes whose ordered centres pass a geometric sanity check (four distinct corners
forming a non-degenerate, correctly ordered quadrilateral); otherwise it falls
back to the classical detector. Because each branch performs the single task of
placing the answer grid at known coordinates and both subsequently feed
the same recognizer, the chosen branch alters only how the sheet is
located, never how an answer is ultimately read.

On the CV branch, the \wasm{} core recovers the page geometry without
external guidance. The \emph{WASM Normalize} stage thresholds the image,
extracts connected components, and retains the four corner registration
markers by filtering candidate blobs on area, aspect ratio, and fill;
when that marker route proves unreliable, it instead falls back to the
white paper boundary. From the four resulting reference points it
estimates a homography onto a canonical $1700\times2400$ template, which
the \emph{Marker Crop} stage applies so that the answer grid is brought
to fixed positions.

On the YOLO branch, the primary configuration is a corner-marker
detector: a single-class YOLOv8n \emph{object} detector (not a pose/keypoint
head) that localizes the four printed corner markers and uses their
bounding-box centres as registration points. The raw image ($1{,}145\times2{,}560$\,px) is first letterboxed into a
$960\times960$ tensor by scaling the longest dimension and zero-padding the
shorter axis, and the model runs through the WebGPU backend. Following inference, the four highest-confidence boxes are reduced to their
centres, mapped back to original-image coordinates by inverting the letterbox
scale and padding, ordered (top-left, top-right, bottom-right, bottom-left), and
passed to the homography that rectifies the sheet onto the canonical
$1700\times2400$ template. This lets the \wasm{} core skip both connected-component
blob detection and the second marker re-detection, so the YOLO branch rejoins the
shared recognizer only at \emph{Adaptive Threshold}. YOLO therefore acts only as a geometric front-end; the answer string is always
decoded by the shared CV recognizer, allowing the handoff to be evaluated
without changing downstream grading.

Once the two branches have rejoined on a common rectified crop,
\emph{Adaptive Threshold} performs local blurring and thresholding, and
\emph{Fixed Grid Bubble Detection} reads the answers. As the sheet now
resides in template coordinates, the grid fixes every bubble center in
advance, so that each option can be scored by the foreground density
inside a circular sampling window and the scores can be normalized within
each row, which prevents a uniformly dark or faint scan from biasing the
decision. The final \emph{Grade Output} stage emits the decoded answer
string together with validity and suspicious-mark flags and the per-stage
timers reported throughout this paper.

Detector-guided cropping is therefore integral to recognition, not a harmless
preprocessing step: any geometric error before the homography displaces the
entire grid.

\subsection{Platform-Specific Optimization and Edge Deployment}
The two deployment targets present complementary trade-offs. The Web Edge
build runs unmodified in the browser sandbox with zero installation, but
accepts virtualization overhead and only managed accelerator access. The
Native Android build instead obtains direct accelerator access and markedly
lower inference latency, at the cost of platform-specific packaging and
maintenance. Because both targets execute all recognition stages locally on the device,
answer-sheet images need not leave it. Latency is comparable across the two
targets only at a matched measurement boundary, which the next section defines.

\section{Experimental Setup}

\subsection{Dataset and Ground Truth}
The evaluation set ($N{=}185$) comprises every annotated sheet in the
corpus: 179 student-answer images and six
answer-key sheets, drawn from five sub-datasets (50, 48, 36, 46, and 5
sheets; \texttt{dataset\_3} holds the low-contrast, re-compressed photos)
and captured on mobile devices (nominally $1{,}145\times2{,}560$\,px for
\texttt{dataset\_1}; other subsets vary).
Dataset~3 is a washed-out, re-compressed subset: all 36 sheets have a
compressed tonal range (median $p_{99}-p_{1}\approx129$ grey levels and paper
white capped at $\approx192/255$, versus $\approx225$–$237$ on the cleanest
subsets), which leaves the printed corner markers close to the
connected-component detection threshold. Answer sheets and answer keys
are the same printed form (a key merely carries the correct marks), so both
are recognized by the identical pipeline, the keys differing only in that
they additionally serve as the grading reference. Two reviewers independently established the ground truth, resolving
disagreements by manual inspection, and marked invalid trailing questions as
non-applicable, yielding 9{,}810 valid question labels and 49{,}050 individual
binary mark decisions behind every accuracy figure in this paper.

\subsection{Detector Training Configuration}
The corner-marker localizer is a single-class (\texttt{marker\_corners})
YOLOv8 nano model fine-tuned from \texttt{yolov8n.pt} on 85 annotated sheets,
split into 68 for training and 17 for validation. Training runs for up to
100 epochs (early stopping, patience 30) at batch size 8 and $960\times960$
input, with the Ultralytics auto-selected optimizer (initial learning rate
0.01, momentum 0.937, weight decay 0.0005); augmentation is intentionally
minimal: small translation (0.1) and scale (0.2) jitter only, with
horizontal/vertical flips, mosaic, and mixup disabled, since the four corner
markers carry a fixed geometric ordering. After convergence the model is
exported to a unified ONNX format shared across the Web and Native
deployments, which removes cross-framework conversion variance; only the
execution provider differs, being WebGPU in the browser and CPU or NNAPI on
Android. Inference uses a $960\times960$ letterboxed input with confidence threshold
$0.05$ (the four highest-confidence boxes are retained) and NMS IoU $0.45$. On the 17-image validation split the
detector obtains $\mathrm{mAP}@0.5{=}0.995$ and recall $1.0$ (all four corner
markers recovered per sheet). Because the detector localizes only the fixed
printed fiducials and never the marked content, and 101 of the 179 student-answer benchmark sheets were never used during
detector development (the 85 development sheets include 78 of these 179 student
sheets; the remaining 7 lie outside the 179-sheet student set), the benchmark recognition
accuracy (Section~\ref{sec:results-recognition}) characterizes the recognizer
given localized corners, separately from this detector validation split.
CV-stage recognition is deterministic and identical across repeated runs and
across Windows hosts.

\subsection{Benchmark Platforms and Hosts}
The benchmark replays the identical 185-image set across five browser/device configurations and
a Native Android baseline on two of them:
\begin{itemize}[leftmargin=*, itemsep=1pt, topsep=2pt]
  \item   \textbf{Desktop reference:} Intel Core i5-14600K, NVIDIA
  RTX~4070 Ti SUPER, 32\,GB RAM.
  \item \textbf{Laptops:} ASUS Vivobook (i5-13500H, 24\,GB RAM, Intel Iris Xe
  iGPU) and Acer Nitro~5 (i5-10300H, 16\,GB RAM).
  \item \textbf{Android (Chrome/Blink):} a Poco Pad~M1 tablet (Snapdragon~7s
  Gen~4, 8\,GB LPDDR4X) and a Redmi Note~13 Pro+ (Dimensity 7200-Ultra,
  8\,GB LPDDR5).

  \item \textbf{Native baseline:} the Poco Pad and the Redmi additionally
  run a native Android application via multi-threaded CPU and NNAPI
  execution providers.
\end{itemize}
Web and Native share the algorithmic stages at the source level but not in
compiled form: OpenCV build, memory layout, SIMD scheduling, and
floating-point ordering all differ between OpenCV.js and OpenCV Android, so
identical inputs need not produce bit-identical outputs. The Native target
exports per-question labels aligned to the reviewed ground truth, so it is
evaluated for both accuracy and latency. For reproducibility, the Web build
runs ONNX Runtime Web on WebGPU with an Emscripten-compiled OpenCV core
using SIMD and threads under cross-origin isolation, and the Native build
runs ONNX Runtime Android with OpenCV~4; every latency host is warmed up
with five sheets, and the five corner-protocol hosts are reported as five-run
medians.

\subsection{Metrics and Measurement Boundaries}
To keep comparisons fair across sandboxed and native environments, metrics
are bounded by the runtime abstraction layer, and each claim is tied to its
artifact and boundary as follows. \emph{Web latency} is a
\emph{worker-pipeline} latency: the worker-side C\texttt{++} (and, for the
hybrid, WebGPU) execution time, measured after image data reaches the worker
thread, so it excludes main-thread decoding and rendering. \emph{Native latency} is the file-based end-to-end
duration, covering image decoding and processing; the debug-only JPEG write
is excluded from reported timings. Because the two boundaries differ (Web excludes decoding while Native includes it), direct Web-Native latency comparisons are reported only on the same-boundary core-stage measurements. \emph{Resource use} is sampled with whichever instrument a host exposes:
process utilities for Windows browsers and an in-app/adb
sampler on Android. A
same-boundary latency ratio uses the corresponding core-stage time (worker-side C\texttt{++} on Web and the native C\texttt{++} core on
Android). Inference ratios compare ORT/WebGPU time on Web with ORT/NNAPI
time on Android. Where deployment latency is discussed the boundary is named
explicitly, and full browser end-to-end wall-time, including main-thread
decoding and rendering, is not exported by the current logs.

Table~\ref{tab:accuracy} reports supervised exact-match recognition on
the reviewed $N{=}185$ fixed-template set. Traditional CV correctly
recognizes 9{,}715 of the 9{,}810 questions, a question-level accuracy of
99.03\%, and reproduces every answer on 143 of the 185 sheets. Replacing
the CV sheet-localization stage with a YOLO corner-marker detector, which
emits the four corner registration markers and feeds their centres directly
to the homography, returns 99.46\% (9{,}757/9{,}810) and 155 of 185 fully
correct sheets, reproducibly across the five corner-protocol hosts. Across this in-distribution benchmark the detector returned four corner markers on
every sheet, so the classical fallback was never exercised; this is a closed-set
result, not tested out-of-distribution robustness. Two quantities must be kept separate here. \emph{Localization accuracy} is measured on the 17-sheet held-out split, where the detector attains $\mathrm{mAP}@0.5{=}0.995$ and recovers all four corners per sheet. The 99.46\% above is instead an \emph{end-to-end recognition} figure: it quantifies how well the deterministic C\texttt{++} core reads bubbles once given accurate corner geometry. Because the corner labels cover part of the evaluation sheets, this is a closed-set, fixed-template bound on recognition given good localization, not a measure of the detector's open-set generalization. On the 101
student-answer sheets never seen during detector development, the corner path
reaches $99.3\%$ question accuracy ($5{,}503/5{,}540$), within noise of the
$99.6\%$ on the 78 detector-development-overlap sheets, suggesting the full-set figure is
not materially inflated by the development overlap.

A bootstrap-by-sheet 95\% confidence interval is 98.63--99.37\% for CV and
99.20--99.68\% for the corner path. Because questions within a sheet are
correlated, we test the difference with a paired bootstrap over the 185
sheets (10{,}000 resamples): the mean per-sheet gain is $+0.45$ points (95\% CI $[+0.20,+0.72]$,
excluding zero), with the corner path better on 32 sheets and worse on 15.
The gain concentrates on the low-contrast \texttt{dataset\_3} photos where
the connected-component marker search is least reliable (CV 97.2\% versus
99.6\% there). In absolute terms this corrects 42 of 9{,}810 questions, a non-negligible
margin when exact sheet-level grading is required. The improvement is therefore
statistically supported but modest in magnitude, and it should still be validated
end-to-end against the fixed-template recognizer rather than inferred from
localization quality alone.

Excluding the six keys, CV and corner score 99.00\% and 99.45\% on the 179
student sheets (keys $\geq$99.6\%), so easy templates do not inflate the figures.
The latency cost of this shift is quantified next.

\label{sec:latency}
Fig.~\ref{fig:latency} and Tables~\ref{tab:stage-mini}--\ref{tab:latency}
report the deployment benchmark, which shows that the Web-versus-Native gap
is larger for the deterministic CV stage than for YOLO inference.

The clearest evidence is a same-device, same-boundary comparison on the
Redmi. For the CV core (the full two-stage normalize, re-crop, threshold and
bubble read, timed worker-side), Native Android
requires $191$\,ms whereas the Mobile Web build requires $503$\,ms, a
$2.6\times$ gap under matched stage boundaries, attributable to the
browser/\wasm{} stack and build-level differences (OpenCV build, memory
layout, SIMD scheduling). The
learned stage behaves very differently: the corner detector takes
$547$\,ms on WebGPU against $335$\,ms for the Native NNAPI provider, a
$1.6\times$ gap that is far smaller than the $4.9\times$ GPU-side browser
slowdown reported for browser deep-learning inference in prior
work~\cite{wang2024}, suggesting that WebGPU can be an effective browser-side
accelerator for this workload. The $312$\,ms CV gap ($503$ vs $191$) is the CV-only figure, which makes the
browser/build-stack CV core the first-order lever in that configuration. In the
hybrid path the residual CV gap shrinks to ${\sim}108$\,ms ($249$ vs ${\sim}141$)
while WebGPU inference adds a $212$\,ms gap ($547$ vs $335$), so a detector-based
deployment is instead inference-bound. The CV core is nonetheless the cost paid
on every sheet regardless of detector, and on phones the inference cost grows
further under CPU execution providers (Table~\ref{tab:stage-mini}).



The Native budget reinforces this attribution
(Table~\ref{tab:stage-mini}). With the complete CV pipeline ported across
(two-stage normalization, the Stage-2 marker re-crop, threshold, and
bubble read), the Native CV core runs in $191$\,ms and recognizes
$97.75\%$ of questions. The residual gap to the Web CV path ($99.03\%$) is
not a limitation of the fixed-grid recognizer but of build-sensitive marker
preprocessing: it is confined to three low-contrast, re-compressed photos
whose marker grey level sits at the detection threshold, so OpenCV-Android
downscaling and thresholding diverge from the Web build's custom kernels by
a few grey levels and reject one marker. This CV-only shortfall is an implementation artifact (a few-grey-level threshold
mismatch), in principle fixable by retuning the Android marker thresholds, rather
than an inherent limitation of the recognizer; the corner-marker path simply
sidesteps it: ported to Native it yields $99.44\%$ on both devices (Redmi and
Poco Pad), on par with the Web hybrid ($99.46\%$) and robust across all five
sub-datasets including the low-contrast subset.
Native keeps the lower
latency while the shared corner-marker path delivers matching,
platform-robust accuracy.



Within the browser, the corner-marker hybrid reshapes the cost structure
rather than merely adding to it (Table~\ref{tab:latency}, five-run medians).
Feeding detector-supplied four-point geometry
to the homography lets the C\texttt{++} core skip both blob detection and the second marker re-detection, roughly
halving its per-sheet latency: $503\to249$\,ms on the Redmi, $343\to166$ on
the Poco Pad, and $325\to138$ on the Vivobook. Whether the full pipeline is
faster is device-dependent: on the Vivobook the C\texttt{++} saving
outweighs the added WebGPU inference (worker time $414\to284$\,ms), whereas
on the phones the $450$--$550$\,ms corner inference dominates and worker time
rises (Redmi $680\to817$\,ms). The hybrid thus moves localization off the
deterministic core and onto the GPU, trading inference latency for a lighter
CV stage at a small accuracy gain.

\subsection{Threats to Validity}
\label{sec:threats}
\begin{enumerate}[label=(\roman*), leftmargin=*, itemsep=1pt, topsep=2pt]
  \item CPU/RAM instruments differ across platforms, so resource values are
indicative rather than comparable efficiency ratios. Stage-level latency tables
report steady-state medians after warm-up, while deployment-level figure bars
report per-sheet means; cold-start asset/model loading is excluded.
  \item The supervised accuracy artifact covers one 185-sheet
  fixed-template collection. This is the intended workload scope rather
  than a claim about arbitrary-layout OMR; broader capture conditions remain future validation.
  \item   Web and Native share source-level stages but differ in OpenCV build,
  floating-point ordering, and memory layout, so outputs are not bit-identical.
  The corner-marker path nonetheless ports at parity ($99.44\%$ vs $99.46\%$);
  the residual CV-only gap traces to build-sensitive marker preprocessing
  (Section~\ref{sec:latency}).
  \item      The detector is developed on 85 sheets ($68/17$ train/validation); the corner
path holds $99.3\%$ on the 101 unseen student-answer benchmark sheets, so the
$99.46\%$ full-set figure is a closed-set, fixed-template result. Writer-disjoint and multi-template
  evaluation remain future work; we claim no generalization beyond this layout.
  \item Web latency on thermally constrained laptops is sensitive to power
  and thermal state: on the Vivobook we saw up to a $\approx 2\times$ spread
  in per-sheet C\texttt{++} latency across runs (outputs bit-identical).
  Corner-protocol hosts are therefore five-run medians, and the
  Web-versus-Native comparison uses the same Redmi device.
\end{enumerate}

\section{Conclusion}

This benchmark shows that Web Edge OMR can be accurate and deployable for
fixed-template grading, yet its latency is set by how the stages balance rather
than by inference alone. The Web CV path reaches 99.03\% question accuracy and the corner-marker
hybrid 99.46\% across five devices, matched at $99.44\%$ when ported to Native.
The learned detector adds only a small but statistically supported accuracy
gain, concentrated in low-contrast captures. On latency, the largest single web-versus-native term in the CV-only path is the
browser/build-stack CV core: on the same Redmi its $503$\,ms is $2.6\times$ the
$191$\,ms native core, wider than the $1.6\times$ between WebGPU and NNAPI; the
hybrid path is instead inference-bound. Native therefore
remains the faster deployment at matching accuracy, while Web Edge exchanges
that latency for privacy and installation-free reach. Closing the gap primarily requires a leaner \wasm{} CV runtime with better browser access to CV acceleration, while mobile hybrid deployments would also benefit from lighter detector inference.
