\begin{abstract}
Browser-based Optical Mark Recognition (OMR) enables on-device grading
without application installation, but the relative impact of the different
stages in a browser-side OMR computation pipeline has not been systematically
quantified. To address this gap, we present a cross-platform Web Edge OMR
framework that integrates WebAssembly (\wasm{}) computer vision with WebGPU
YOLO inference, and evaluate it on a fixed-template 185-sheet dataset
across seven browser/device configurations, comparing the results with a
Native Android implementation on two of them.
Our stage attribution reveals that the web-versus-native latency gap is
larger for deterministic \wasm{} computer vision than for WebGPU YOLO
inference, though detector inference remains a substantial absolute cost on
phones. On the 185-sheet set, the matched-boundary computer-vision stage on
Mobile Web is $2.6\times$ slower than its Native counterpart, whereas the
corner detector's inference on WebGPU is only $1.6\times$ slower than Native
NNAPI. Despite this latency gap, the Web
pipeline reaches $99.03\%$ question accuracy with classical computer vision
and $99.46\%$ with the corner-marker detector; on this closed-set
fixed-template benchmark the detector yields a small paired gain
($+0.4$ points) that must be validated end-to-end against the
fixed-template recognizer rather than assumed from localization quality ---
and the same corner-marker path, ported to Native, reaches matching
accuracy ($99.44\%$). These findings indicate that
optimizing Web Edge OMR should primarily target the \wasm{} computer-vision
stage, while mobile hybrid deployments would also benefit from lighter
detector inference; they support
browser-based grading as a privacy-preserving, installation-free
alternative to native deployment.
\end{abstract}

\section{Introduction}

Automated grading of multiple-choice answer sheets is widely used in
educational institutions, where large volumes of sheets must be
processed accurately within a short time. Existing deployments follow
two established patterns. Server-based services transmit scanned or
photographed sheets to remote infrastructure, introducing network
dependency and exposing student data to external
systems~\cite{patel2015,okorie2022}. Native mobile applications avoid
data transmission but require platform-specific packaging, app-store
distribution, and per-platform maintenance overhead.

Recent maturation of \wasm{} and WebGPU now allows computer-vision and
deep-learning workloads to execute directly inside modern browsers
without plugins or installation, which enables a third deployment model:
a fully client-side pipeline in which answer-sheet images are processed
within the browser and never leave the device. Because a single
URL-deployed bundle serves both desktop and mobile browsers, this model
avoids the data-exposure risk inherent in server-side grading while also
removing the installation friction of a native application.

In the browser these workloads map onto two different substrates. The
classical image-processing stages, namely perspective rectification,
adaptive thresholding, and fixed-grid bubble reading, are compiled from
C\texttt{++}/OpenCV to \wasm{} and run on the CPU, whereas sheet-region
localization can optionally be offloaded to neural inference through ONNX
Runtime Web on a WebGPU backend. A deployment may thus run a CV-only
pipeline or add a YOLO detector for the localization step; because the two
substrates use different browser APIs and hardware, it is their relative
cost rather than either component in isolation that determines whether a
given configuration can rival native execution. This benchmark measures
both.

Despite the potential of this heterogeneous web pipeline, the exact
interplay between CPU-bound \wasm{} computer vision and GPU-accelerated deep
learning inside the browser remains unquantified. Crucially, it is unclear
whether accelerating inference via WebGPU is sufficient to close the
performance gap with native platforms. To address this, this paper presents
a systematic empirical study that benchmarks a complete Web Edge OMR
pipeline against a Native Android baseline. Our findings reveal a critical
shift: while WebGPU significantly reduces YOLO latency, the deterministic
CV/\wasm{} stage is the larger source of the web-versus-native latency gap.
Consequently, browser-based OMR emerges as a highly viable, privacy-preserving
alternative whose ultimate competitiveness hinges primarily on minimizing
\wasm{} computational overhead, while mobile hybrid deployments may still
benefit from lighter detector inference.

The paper makes three contributions:
\begin{enumerate}[leftmargin=*, itemsep=1pt, topsep=2pt]
  \item We provide a human-reviewed cross-platform benchmark for Web Edge
  OMR using a 185-sheet fixed-template dataset, with supervised measurements
  of accuracy and latency across seven browser/device configurations ---
  plus indicative resource measurements on the hosts that expose
  process-level instrumentation --- and a Native Android baseline on two of
  them.
  \item We perform a stage-level attribution analysis that separates
  browser-based computer vision and neural-inference costs, demonstrating
  that the web-versus-native latency gap is larger for the deterministic
  \wasm{} computer-vision stage than for WebGPU-accelerated YOLO inference.
  \item We demonstrate, through a detector-handoff analysis, that a YOLO
  corner-marker localizer can act as a primary front-end validated on this
  fixed-template benchmark --- matching or slightly exceeding classical-CV
  recognition on both Web and Native and offloading localization to the
  GPU --- while also showing that the localizer yields only a small accuracy
  gain, so detector outputs must be validated end-to-end with the
  fixed-template recognizer rather than assumed from localization quality.
\end{enumerate}

\section{Related Work}

\paragraph{Classical OMR}
Traditional OMR pipelines rely on handcrafted image-processing
techniques such as thresholding, edge detection, and morphological
operations for bubble localization and recognition~\cite{patel2015,okorie2022}.
Although computationally efficient, these methods remain sensitive to
illumination variation and geometric distortion in mobile capture
scenarios~\cite{afifi2019}.

\paragraph{Deep learning for OMR}
Recent studies adopt YOLO-based detectors~\cite{redmon2016} to improve
robustness under challenging imaging conditions. Ali et
al.~\cite{ali2025} summarize evidence that YOLO-based detectors improve
detection robustness over threshold-based methods, while
YOLOv8n~\cite{jocher2023} provides a lightweight architecture suitable
for edge deployment. Tabassum and Rahman~\cite{tabassum2024} deploy
YOLOv8 for mobile OMR but report neither stage-level latency
decomposition nor a controlled cross-platform comparison, leaving
unclear how inference cost relates to the surrounding CV pipeline on
constrained devices.

\paragraph{Browser-based edge computing}
\wasm{} and WebGPU~\cite{webgpu2025} together enable privacy-preserving
client-side execution in modern browsers, with neural inference exposed
through ONNX Runtime Web~\cite{microsoft2021}. Quantitative evidence on the associated
overhead is already available: Jangda et al.~\cite{jangda2019} report
that \wasm{} runs on average 45\% slower than native code on
compute-intensive benchmarks, a margin that is directly relevant to
C\texttt{++} image-processing workloads compiled to \wasm{}, and Wang et
al.~\cite{wang2024} measure browser deep-learning inference at
$16.9\times$ slower than native on CPU and $4.9\times$ on GPU, with
WebGPU emerging as the strongest browser-side back-end. These studies,
however, characterize isolated kernels rather than complete
computer-vision pipelines. A higher-level abstraction is also emerging in
the W3C WebNN API~\cite{webnn2026}, yet it remains a draft, so the
practical interaction between \wasm{}-based image processing and WebGPU
inference within a full application is still poorly understood.

\paragraph{Research gap}
Prior work thus examines either OMR accuracy or browser inference
performance, but rarely both within one system. To our knowledge, no prior
study evaluates a fully client-side browser OMR pipeline --- computer vision
and neural inference both executing locally, with no transmission of
answer-sheet data --- or establishes whether its latency is governed by
neural inference or by the \wasm{}-executed computer-vision stages. The
present paper closes these gaps through controlled per-stage profiling of a
YOLOv8n-based browser OMR system across several back-ends and deployment
configurations.

\section{System Architecture and Methods}

\begin{figure}[t]
  \centering

  dispatches camera or file input to a Web Worker. WebGPU accelerates
  only YOLO localization; normalization, thresholding, bubble reading,
  and grading remain in the \wasm{} C\texttt{++}/OpenCV core.}
  \label{fig:arch}
\end{figure}

\subsection{Cross-Platform Layered Architecture}
The system is organized as the layered runtime shown in
Fig.~\ref{fig:arch}(a), where each layer hides the one beneath it so that
the same application code runs unchanged on heterogeneous hardware. At the
top, the JavaScript main thread owns user interaction and image
acquisition from a camera stream or an uploaded file, but it delegates all
computation to a dedicated Web Worker so that heavy processing never
blocks UI responsiveness. Within the worker, an Algorithm Dispatcher
selects between a conventional CV-only pipeline and a hybrid YOLO$+$CV
pipeline; in the hybrid case it drives an ONNX YOLO model on a WebGPU
backend for localization, while the \wasm{} OMR core --- hand-written
C\texttt{++} image-processing kernels together with OpenCV, compiled to
\wasm{} --- performs the actual recognition and grading. Since the dispatcher feeds
any localization output into that same \wasm{} core, the two pipelines
remain interchangeable at the recognition stage. Both back-ends ultimately
execute inside the OS and browser sandbox, which mediates scheduling,
memory, and security before mapping the work onto whatever CPU, GPU, or
NPU the device exposes. This separation lets a single codebase target
desktop and mobile platforms without modification.

\subsection{Algorithmic Pipelines and Handoff Mechanism}

Fig.~\ref{fig:arch}(b) traces a single sheet from capture to score along
a predominantly linear spine, comprising the Input Frame, JS Decode \&
Prep, Method Selection, a detect stage, Fixed Grid Bubble Detection, and
Grade Output. Detection is the only stage that forks: it splits into a CV
branch and a YOLO branch, both of which converge again before grading so
that the remainder of the pipeline is identical in either configuration.

The main thread first hands the worker a raw frame or uploaded image,
here at $1{,}145\times2{,}560$\,px. \emph{JS Decode \& Prep} renders this
image onto a canvas and derives the two artifacts that the downstream
stages require, namely an RGBA pixel buffer for the \wasm{} core and,
whenever the hybrid path is selected, a letterboxed tensor for the YOLO
detector ($960\times960$ for the primary corner-marker model).
\emph{Method Selection} then routes the image into one of the
two detect branches. Because each branch performs the single task of
placing the answer grid at known coordinates and both subsequently feed
the same recognizer, the chosen branch alters only how the sheet is
located, never how an answer is ultimately read.

On the CV branch, the \wasm{} core recovers the page geometry without
external guidance. The \emph{Normalize} stage thresholds the image,
extracts connected components, and retains the four corner registration
markers by filtering candidate blobs on area, aspect ratio, and fill;
when that marker route proves unreliable, it instead falls back to the
white paper boundary. From the four resulting reference points it
estimates a homography onto a canonical $1700\times2400$ template, which
the \emph{Marker Crop} stage applies so that the answer grid is brought
to fixed positions.

On the YOLO branch, the primary configuration is a corner-marker
detector: a single-class YOLOv8n \emph{object} detector (not a pose/keypoint
head) that localizes the four printed corner markers and uses their
bounding-box centres as registration points. The image is \emph{letterboxed}
into a $960\times960$ square (scaled to fit while padding the margin), and the
model runs through the WebGPU backend. The four highest-confidence detections
are reduced to their centres, geometrically ordered into top-left, top-right,
bottom-right, and bottom-left, and passed
\emph{directly} to the homography that rectifies the sheet onto the
canonical template. This lets the \wasm{} core skip both the
connected-component blob detection of the CV \emph{Normalize} stage and the
second marker re-detection, so the YOLO branch rejoins the shared
recognizer only at the \emph{Adaptive Threshold} stage. YOLO thus
contributes localization alone, since the answer string is invariably
decoded by the CV recognizer rather than by the detector. This strict
decoupling makes the detector a purely geometric front-end, so the
localization handoff can be evaluated without changing downstream grading.

Once the two branches have rejoined on a common rectified crop,
\emph{Adaptive Threshold} performs local blurring and thresholding, and
\emph{Fixed Grid Bubble Detection} reads the answers. As the sheet now
resides in template coordinates, the grid fixes every bubble center in
advance, so that each option can be scored by the foreground density
inside a circular sampling window and the scores can be normalized within
each row, which prevents a uniformly dark or faint scan from biasing the
decision. The final \emph{Grade Output} stage emits the decoded answer
string together with validity and suspicious-mark flags and the per-stage
timers reported throughout this paper.

Because the recognizer is deterministic, any geometric error before the
homography displaces the entire grid --- so detector-guided cropping is an
integral part of the recognition algorithm, not a harmless preprocessing
step.

\subsection{Platform-Specific Optimization and Edge Deployment}
The framework targets two deployment environments with complementary
trade-offs. The Web Edge build uses \wasm{} via OpenCV.js for deterministic
image processing and WebGPU via ONNX Runtime Web for inference, enabling
zero-installation cross-platform execution in the browser sandbox, at the
cost of virtualization overhead and only managed accelerator access. The
Native Android build uses the OpenCV Android SDK through JNI and ONNX Runtime
Android, granting direct access to the Neural Networks API (NNAPI) and
markedly lower inference latency, at the cost of packaging and per-platform
maintenance. Both execute every stage locally on the device: this removes
network latency from recognition and is privacy-preserving by design, since
the answer-sheet images need not leave the device during recognition
(assuming the deployed application performs no upload or telemetry; offline
operation further requires cached or PWA-installed assets). It is also what
makes a like-for-like latency comparison between the two targets meaningful.

\section{Experimental Setup}

\subsection{Dataset and Ground Truth}
The evaluation set ($N{=}185$) comprises every annotated sheet in the
corpus: 179 student-answer images and six
answer-key sheets, drawn from five sub-datasets (50, 48, 36, 46, and 5
sheets; \texttt{dataset\_3} holds the low-contrast, re-compressed photos)
and each captured at $1{,}145\times2{,}560$\,px on a mobile device. Answer sheets and answer keys
are the same printed form---a key merely carries the correct marks---so both
are recognized by the identical pipeline, the keys differing only in that
they additionally serve as the grading reference. A human-reviewed reference
establishes the ground truth and marks invalid trailing questions as
non-applicable, yielding 9{,}810 valid question labels and 49{,}050
individual binary mark decisions behind every accuracy figure in this paper.

\subsection{Detector Training Configuration}
The corner-marker localizer is a single-class YOLOv8 nano model trained on
the 185 annotated sheets, split into 159 images for training and 26 for
validation under the standard Ultralytics YOLOv8 recipe. After convergence
the model is exported to a unified ONNX format shared across the Web and
Native deployments, which removes cross-framework conversion variance; only
the execution provider differs, being WebGPU in the browser and CPU or NNAPI
on Android. Inference uses a $960\times960$ letterboxed input with confidence
threshold $0.05$ and NMS IoU $0.45$. On the 26-image validation split the
detector obtains $\mathrm{mAP}@0.5{=}0.995$ and recall $1.0$ (all four corner
markers recovered per sheet); CV-stage recognition is deterministic and
identical across repeated runs and across Windows hosts.

\subsection{Benchmark Platforms and Hosts}
The benchmark replays the identical 185-image set across seven browser/device configurations and
a Native Android baseline on two of them:
\begin{itemize}[leftmargin=*, itemsep=1pt, topsep=2pt]
  \item \textbf{Desktop reference:} Intel Core i5-14600K with an NVIDIA
  RTX~4070 Ti SUPER.
  \item \textbf{Laptops:} ASUS Vivobook (i5-13500H) and Acer Nitro~5
  (i5-10300H).
  \item \textbf{Apple:} a MacBook Air~M1 and an iPhone~16 (Safari/WebKit).
  \item \textbf{Android (Chrome/Blink):} a Poco Pad~M1 tablet and a Redmi
  Note~13 Pro+.
  \item \textbf{Native baseline:} the Poco Pad and the Redmi additionally
  run a native Android application via multi-threaded CPU and NNAPI
  execution providers.
\end{itemize}
Web and Native share the algorithmic stages at the source level but not in
compiled form: OpenCV build, memory layout, SIMD scheduling, and
floating-point ordering all differ between OpenCV.js and OpenCV Android, so
identical inputs need not produce bit-identical outputs. The Native target
exports per-question labels aligned to the reviewed ground truth, so it is
evaluated for both accuracy and latency. For reproducibility, the Web build
runs ONNX Runtime Web on WebGPU with an Emscripten-compiled OpenCV core
using SIMD and threads under cross-origin isolation, and the Native build
runs ONNX Runtime Android with OpenCV~4; every latency host is warmed up
with five sheets, and the five corner-protocol hosts are reported as five-run
medians (the Mac and iPhone as an earlier single round).

\subsection{Metrics and Measurement Boundaries}
To keep comparisons fair across sandboxed and native environments, metrics
are bounded by the runtime abstraction layer, and each claim is tied to its
artifact and boundary as follows. \emph{Web latency} is a
\emph{worker-pipeline} latency: the worker-side C\texttt{++} (and, for the
hybrid, WebGPU) execution time, measured after image data reaches the worker
thread, so it excludes main-thread decoding and rendering and is therefore a
lower bound on the full browser wall-time rather than a complete
device-to-grade time. \emph{Native latency} is the file-based end-to-end
duration, covering image decoding and processing; the debug-only JPEG write
is excluded from reported timings. \emph{Resource use} is sampled with
whichever instrument a host exposes: process utilities for Windows browsers,
an in-page event-loop-lag proxy where direct process sampling is
unavailable (Mac and iOS), and an in-app/adb sampler on Android. A
same-boundary latency ratio uses the corresponding core-stage time ---
worker-side C\texttt{++} on Web and the native C\texttt{++} core on
Android, and inference ratios compare ORT/WebGPU time on Web with ORT/NNAPI
time on Android. Where deployment latency is discussed the boundary is named
explicitly, and Web browser wall-time is not exported by the current logs.

\section{Results and Discussion}

\subsection{Recognition Accuracy}
\label{sec:results-recognition}

Table~\ref{tab:accuracy} reports supervised exact-match recognition on
the reviewed $N{=}185$ fixed-template set. Traditional CV correctly
recognizes 9{,}715 of the 9{,}810 questions, a question-level accuracy of
99.03\%, and reproduces every answer on 143 of the 185 sheets. Replacing
the CV sheet-localization stage with a YOLO corner-marker detector, which
emits the four corner registration markers and feeds their centres directly
to the homography, returns 99.46\% (9{,}757/9{,}810) and 155 of 185 fully
correct sheets, reproducibly across the five corner-protocol hosts.

A bootstrap-by-sheet 95\% confidence interval is 98.63--99.37\% for CV and
99.20--99.68\% for the corner path. Because questions within a sheet are
correlated, we test the difference with a paired bootstrap over the 185
sheets (10{,}000 resamples): the mean per-sheet gain is $+0.45$ points (95\% CI $[+0.20,+0.72]$,
excluding zero), with the corner path better on 32 sheets and worse on 15.
The gain concentrates on the low-contrast \texttt{dataset\_3} photos where
the connected-component marker search is least reliable (CV 97.2\% versus
99.6\% there). The corner-marker formulation is therefore not merely
accuracy-neutral; it gives a modest but real improvement that ---
crucially --- must be validated end-to-end against the fixed-template
recognizer rather than assumed from localization quality alone.

Beyond accuracy, passing four exact corner points to the homography removes
the connected-component marker detection and its second re-detection pass
from the C\texttt{++} core and moves the localization onto the GPU; the
latency results below show the resulting shift in where the per-sheet cost
is spent. On the 179 student sheets alone CV scores 99.00\% and the corner
path 99.45\% (both $\geq$99.6\% on the six keys), so the metrics are not
inflated by easy templates. At the bubble level the CV baseline attains
Precision 0.992,
Recall 0.994, and F1 0.993 over the 49{,}050 binary decisions, and the
corner-marker pipeline edges it at 0.995/0.998/0.997.

\subsection{Cross-Platform Latency}
\label{sec:latency}
Fig.~\ref{fig:latency} and Tables~\ref{tab:stage-mini}--\ref{tab:latency}
report the deployment benchmark, which shows that the Web-versus-Native gap
is larger for the deterministic CV stage than for YOLO inference, although
on mobile hybrid runs the absolute WebGPU inference time remains a major
contributor to the worker pipeline.

The clearest evidence is a same-device, same-boundary comparison on the
Redmi. For the CV core (the full two-stage normalize, re-crop, threshold and
bubble read, timed worker-side), Native Android
requires $191$\,ms whereas the Mobile Web build requires $503$\,ms, a
$2.6\times$ gap under matched stage boundaries, attributable to the
browser/\wasm{} execution stack together with build-level differences such
as memory layout, SIMD scheduling, and OpenCV implementation. The
learned stage behaves very differently: the corner detector takes
$547$\,ms on WebGPU against $335$\,ms for the Native NNAPI provider, a
$1.6\times$ gap that is far smaller than the $4.9\times$ GPU-side browser
slowdown reported for browser deep-learning inference in prior
work~\cite{wang2024}, which shows that WebGPU is already an effective
accelerator. Since the CV gap exceeds the inference gap in both relative
($2.6\times$ vs $1.6\times$) and absolute ($312$ vs $212$\,ms) terms, and
the CV stage runs on every sheet irrespective of the detector, the
first-order lever for Web Edge latency is the \wasm{} CV runtime --- though
the detector remains a substantial absolute cost on phones.

The Native budget reinforces this attribution
(Table~\ref{tab:stage-mini}). With the complete CV pipeline ported across
--- two-stage normalization, the Stage-2 marker re-crop, threshold, and
bubble read --- the Native CV core runs in $191$\,ms and recognizes
$97.75\%$ of questions. The residual gap to the Web CV path ($99.03\%$) is
not a limitation of the fixed-grid recognizer but of build-sensitive marker
preprocessing: it is confined to three low-contrast, re-compressed photos
whose marker grey level sits at the detection threshold, so OpenCV-Android
downscaling and thresholding diverge from the Web build's custom kernels by
a few grey levels and reject one marker. The corner-marker path removes
exactly this implementation sensitivity: ported to Native it yields
$99.44\%$ on both devices (Redmi and Poco Pad), on par with the Web hybrid
($99.46\%$) and correct on all five sub-datasets including the dark sheets.
The web-versus-native penalty is thus concentrated in the \wasm{} CV
runtime, not the GPU-accelerated detector, and Native keeps the lower
latency while the shared corner-marker path delivers matching,
platform-robust accuracy.

Within the browser, the corner-marker hybrid reshapes the cost structure
rather than merely adding to it (Table~\ref{tab:latency}, five-run medians).
Feeding an exact four-point geometry to the homography lets the C\texttt{++}
core skip both blob detection and the second marker re-detection, roughly
halving its per-sheet latency: $503\to249$\,ms on the Redmi, $343\to166$ on
the Poco Pad, and $325\to138$ on the Vivobook. Whether the full pipeline is
faster is device-dependent: on the Vivobook the C\texttt{++} saving
outweighs the added WebGPU inference (worker time $379\to278$\,ms), whereas
on the phones the $450$--$550$\,ms corner inference dominates and worker time
rises (Redmi $683\to805$\,ms). The hybrid thus moves localization off the
deterministic core and onto the GPU, trading inference latency for a lighter
CV stage at a small accuracy gain.

\subsection{Threats to Validity}
\label{sec:threats}
\begin{enumerate}[label=(\roman*), leftmargin=*, itemsep=1pt, topsep=2pt]
  \item CPU/RAM instruments differ across platforms, so resource values
  are reported with their native units and used for trend interpretation
  rather than direct cross-instrument ratios. All latencies are
  steady-state batch medians after warm-up; cold-start asset and model
  loading is excluded.
  \item The supervised accuracy artifact covers one 185-sheet
  fixed-template collection. This is the intended workload scope rather
  than a claim about arbitrary-layout OMR; writer-disjoint data and
  broader capture conditions remain future validation.
  \item Web and Native share source-level stages but differ in OpenCV build,
  floating-point ordering, and memory layout, so outputs are not
  bit-identical. The corner-marker path ports at parity ($99.44\%$ vs
  $99.46\%$); the ported CV-only path reaches $97.75\%$, the $1.3$-point gap
  confined to three borderline-contrast sheets where hand-tuned marker
  thresholds are build-sensitive --- itself evidence for the fiducial
  front-end.
  \item The detector is trained on the 185 sheets ($159/26$ split). Because
  the corner labels include the evaluation sheets, the $99.46\%$ figure is a
  closed-set,
  fixed-template result; writer-disjoint and multi-template evaluation remain
  future work, so we avoid any claim of generalization beyond this layout.
  \item Web latency on thermally constrained laptops is sensitive to power
  and thermal state: on the Vivobook we saw up to a $\approx 2\times$ spread
  in per-sheet C\texttt{++} latency across runs (outputs bit-identical).
  Corner-protocol hosts are therefore five-run medians, and the
  Web-versus-Native comparison uses the same Redmi device.
\end{enumerate}

\section{Conclusion}

Web Edge OMR proves to be both accurate and deployable, yet its latency
is determined by how the stages balance rather than by inference alone.
The reviewed Web CV path reaches 99.03\% question accuracy, and a YOLO
corner-marker detector that feeds four predicted markers straight into
the homography reaches 99.46\% across five devices --- a small but
statistically significant gain on this closed-set fixed-template
benchmark --- and, ported to Native, attains a matching $99.44\%$ there as
well, while moving localization onto the GPU and removing the hand-written
marker detection. On latency,
the dominant web-versus-native term is the \wasm{} CV stage: on the same
Redmi device its $503$\,ms is $2.6\times$ the $191$\,ms native core, a
larger gap than the $1.6\times$ between WebGPU and NNAPI for the same
detector. Native Android therefore remains the faster deployment --- now at
matching accuracy --- while Web Edge exchanges that latency for privacy and
installation-free reach. As a deployment rule: prefer Native when
installation is acceptable and latency is paramount, Web for reach and
privacy; within either, prefer the corner-marker front-end on low-contrast
sheets and CV-only when markers are clean. Closing the
web-versus-native gap primarily requires browser-accessible CV acceleration
and a leaner \wasm{} runtime, while mobile hybrid deployments would also
benefit from lighter detector inference.
